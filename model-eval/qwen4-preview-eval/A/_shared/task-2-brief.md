# 任务 2 · 接手一个别人跑路留下的服务，判断它能不能上线

外包团队做到一半人联系不上了。你拿到一份 `orders.js`，老板明天要决定：**这个后端能不能直接接支付上线，还是要重写。**

## 输入

`../_shared/assets/legacy_orders.js`

## 你要交付的

### 1. `2/FINDINGS.md`，按这个模板，每个问题一节

```markdown
## 问题 N：一句话标题
- **位置**：函数名 / 行号
- **后果**：会发生什么，具体到"谁会在什么时候被坑"
- **严重度**：致命 / 严重 / 一般
- **修法**：一句话，不要贴代码
```

宁可少写也不要凑数——**误报比漏报扣得多**。每条都要能指到具体代码。

### 2. `2/patched/` 里放改好的代码

只改你认为必须改的，不要重写整个文件。改了什么在 `FINDINGS.md` 末尾列一行清单。

### 3. 最后回答一个问题（写在 `FINDINGS.md` 最上方，三行以内）

> 明天能不能直接上线？如果不能，最少改哪几处才能上？

## 硬约束

- 不许改输入文件，副本放 `2/patched/`。
- 不许写"建议引入 TypeScript / 加单元测试 / 上 CI"这种正确但没用的话——那些不算问题。
- 一个问题一节，不要合并。

## 你会怎么被评

有一个已知问题清单（你事先看不到）。评分人按"找到几个 / 误报几个"对表，
另外看你的上线判断是不是跟问题严重度对得上。

时间是 20–30 分钟的量级。**不要为了找全而把整个文件重写一遍。**
